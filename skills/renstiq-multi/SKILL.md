# 複数repoのPR処理

coordinatorは対象の確定、repo担当sub-agentへの委譲、報告の確認・集約を行う。repo共通の調査・操作・後処理・最終確認には [renstiq-single](../renstiq-single/SKILL.md) を使い、ここに二重実装しない。

指定された対象、実行場所、共通設定、調査のみか操作まで行うかを引き継ぐ。`--config FILE` が指定されていれば全担当者へ同じ値を渡す。AGENTS.mdやautomationの追加指示に従う。

## 対象の確定

```sh
renstiq discover --all
```

- stdoutの `discovery` と `errors`、stderr、終了コードを読む。`enabled` は処理対象、`disabled`・`no_config`・`excluded` は通常の状態として理由を保持する。`config_error`・`discovery_error`・`repository_error` があっても、成功している残りのrepoは続ける。
- 最初の対象一覧を保持し、明示されたrepo一覧と照合する。「全部」は元の一覧を網羅し、独自分類や件数で絞らない。指定repoが探索結果にない場合も処理不能の理由を調べ、無言で除外しない。
- 探索対象が空なら「対象repoなし」と報告する。共通設定不正などで対象を取得できなかった場合は「0件」とせず探索失敗と報告する。探索範囲を推測で広げたり、設定を勝手に作成・有効化したりしない。

## 委譲

各対象repoに一人の担当sub-agentを割り当て、singleを読んで開始から最終報告まで担当させる。対象repoのローカルパス、共通設定、PRの限定、操作の許可範囲、利用側の追加指示、必要な報告項目を渡す。担当者間でrepo固有設定・判断・作業場所を混ぜない。

repo間の実行方法は利用側の指示を優先する。元のautomationの「repo間並列・同一repo内直列」を引き継ぎ、並列指定なら複数担当者を同時に進める。一件の失敗で他repoを止めない。実行方法の指定がなければrepoごとに担当者を起動し、報告を確認してから次のrepoへ進む。同一repoに複数担当者を同時に割り当てない。

## 報告の確認と集約

担当者の報告を、singleの最終報告項目と照合する。特に次の不足を見落とさない。

- 開始時・終了時のopen数と候補の内訳、取得失敗による不明数、候補0件とopen PR0件の区別。
- PRごとのマージ/保留理由、checks・changelog・impactの根拠、実施した操作と結果。
- 後処理の必要性と結果、結果不明・未移行・処理不能の理由、ローカル変更。
- 最終 `pr list --all` とローカル状態確認、新規PRを含む残件、ユーザーの確認方法。

不足は同じ担当者へ具体的に戻し、必要な確認と報告の追記を依頼する。最終確認のない報告を完了扱いしない。担当者が確認できなければ、その理由を未完了として受け取る。通常はcoordinatorがGitHubを二重確認しない。報告に矛盾があり、担当者への追加確認でも解消できない場合だけ、必要最小限の直接確認を行う。

全対象repoについて結果または処理不能の理由がそろったら、最初の一覧と照合して全体サマリを報告する。完了・保留・失敗・未完了、マージ数、開始/終了件数、後処理、エラーと残件をまとめる。不明件数があるときは既知分の合計と区別する。探索で無効・未設定・除外だったrepoも理由を残し、ユーザーが確認できる `renstiq discover --all`、対象repoの `renstiq pr list --repo REPO_DIR --all` とPR URLを添える。
